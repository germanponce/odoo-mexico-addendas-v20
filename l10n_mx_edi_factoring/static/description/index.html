¿Qué hace este módulo?

Implementa Factoraje Financiero en el flujo de Cuentas por Cobrar de Odoo con timbrado CFDI completo. Permite que un factorante liquide las facturas de los clientes, generando el asiento de compensación y emitiendo el CFDI de Pago 2.0 con dos nodos pago20:Pago: uno para el pago ordinario (al factorante) y otro para el movimiento de factoraje (FormaDePago 17).

Migración v18 → v19: El template payment20.xml pasó de ser un override completo a una herencia del template oficial l10n_mx_edi.payment20 de v19 vía xpath. Se eliminaron los print(), se renombró tree → list y se corrigieron los attrs a invisible directo.

Cambios de Migración v18 → v19

❌ payment20.xml: override completo → herencia

En v18 el archivo era una copia completa del template de pagos con modificaciones. En v19 usa <template inherit_id="l10n_mx_edi.payment20"> con un xpath que añade el segundo <pago20:Pago> después del primero. Esto es correcto porque v19 utiliza su propio template oficial que puede cambiar entre versiones menores.

❌ print() eliminado

action_register_payment en v18 tenía un print() de depuración. Eliminado en v19. El contexto default_x_factoring_partner_id sigue propagándose al wizard correctamente.

❌ tree → list en vistas XML

El elemento <tree> en account_factoring.xml fue renombrado a <list>, que es la forma correcta en v17+.

❌ attrs → invisible directo

El campo x_factoring_partner_id en la vista del partner usaba attrs="{'invisible': [...]}". En v19 se usa invisible="not x_is_factoring_partner" directamente.

✅ Renombrado add_factoring_invoices → _add_factoring_cfdi_values

El método fue renombrado con prefijo privado _ y nombre más descriptivo siguiendo las convenciones de v19. La lógica interna no cambió.

✅ compute_ → _compute_ en wizard

Los métodos compute del wizard (compute_bill_amount, etc.) fueron renombrados con prefijo _compute_ siguiendo la convención de Odoo v19. Los campos compute= se actualizaron acorde.

✅ XPath con *[name()='pago20:Pago']

En v19, para hacer XPath sobre elementos con namespace en templates QWeb se usa *[name()='pago20:Pago'] en lugar de //pago20:Pago, lo que evita problemas con la resolución de namespaces en lxml.

✅ js_assign_outstanding_line confirmado en v19

El método js_assign_outstanding_line(line_id) sigue disponible en v19 sobre account.move. Internamente llama a .reconcile() sobre las líneas correspondientes.

Estructura del CFDI de Pago generado

cfdi:Comprobante TipoDeComprobante="P"
  cfdi:Emisor  → La empresa (emisor del CFDI)
  cfdi:Receptor → El Factorante Financiero (no el cliente original)
  cfdi:Conceptos → Concepto genérico (84111506 / ACT / Pago)
  cfdi:Complemento
    pago20:Pagos Version="2.0"
      pago20:Totales → Suma de ambos nodos Pago
      
      ┌─ pago20:Pago #1 ─────────────────────────── (pago ordinario) ─┐
      │  FormaDePagoP = XX  (la forma seleccionada en el wizard)        │
      │  pago20:DoctoRelacionado → Facturas del cliente                 │
      └────────────────────────────────────────────────────────────────┘
      
      ┌─ pago20:Pago #2 ─────────────────────────── (factoraje FDP=17) ┐
      │  FormaDePagoP = "17"  (Compensación de deudas)                  │
      │  pago20:DoctoRelacionado → Mismas facturas con datos del         │
      │                             asiento de compensación              │
      └────────────────────────────────────────────────────────────────┘

⚠️ Notas importantes de implementación

1. Verificar _l10n_mx_edi_add_payment_cfdi_values en producción: Si al timbrar el pago el XML no contiene el segundo pago20:Pago, verificar que el método base sigue siendo llamado desde l10n_mx_edi.document con la misma clave pay_results['invoice_results']. En caso de cambio, ajustar el acceso al dict.

2. Relación Many2many x_factoring_invoice_ids: La tabla ir_acc_factoring_rel solo tiene la columna factoring_id definida. Si Odoo reporta un conflicto de columna al instalar, agrega también column2='move_id' en la definición del campo.

3. Método de pago SAT código 17: El asiento de compensación usa l10n_mx_edi.payment.method con código '17' (Compensación de deudas). Verificar que este registro exista en la base de datos antes de ejecutar el factoraje.

4. XPath del payment20: El xpath //*[name()='pago20:Pago'] apunta al primer elemento con ese nombre en el árbol. Si en el futuro el template oficial de v19 agrega más nodos pago20:Pago, puede ser necesario ajustar el xpath para ser más específico.
